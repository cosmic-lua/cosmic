note: tinfl builds an incomplete Huffman table -- no codes at all, or one code, which it allows -- leaving the fast lookup's unused slots 0, and decoding one reads as symbol 0 of length 0: nothing consumed. A literal/length table with no codes then yields literal 0 forever from a few bytes of input (a dynamic block whose code lengths are all zero), and tinfl never asks for more, so every caller spins. zlib marks those slots invalid and fails on them ("invalid literal/length code", "invalid distance code"); this does the same for a symbol decoded through TINFL_HUFF_DECODE (code lengths, the slow literal/length path, distances). State 100 + the macro's own index is its failing state, clear of every index tinfl uses (1 to 54). Upstream 3.1.2 fails on code_len == 0 only in the fast literal/length path's two lookups (states 40 and 54, after the lookup and before anything is written), which is all that path needs: it fails exactly where a record here did before 3.1.2, so those records are gone. Its TINFL_HUFF_DECODE still has no such check, so this one stays; without it the slow path spins on literal 0 as above.
